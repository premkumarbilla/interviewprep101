CDN

Route each user to the nearest edge via DNS/anycast, serve from a tiered cache (edge → regional shield → origin), and invalidate through a global control plane.

Requirements

Functional

  • Serve static content (images, video, JS/CSS) from edge locations near users.
  • Fetch from the origin on a cache miss, then cache the response.
  • Honor cache rules: TTLs, cache-control headers, query-string handling.
  • Purge or invalidate content on demand.
  • Route each user to the nearest healthy edge.
  • Support custom domains with HTTPS.

Non-functional

  • Global scale: hundreds of edge locations, millions of requests/sec.
  • Latency: edge hits under ~50 ms for most users.
  • Availability: 99.99%+; an edge failure reroutes users automatically.
  • Cache hit ratio above 90% to protect origins.
  • Purges propagate globally within seconds to a few minutes.
  • Security: DDoS absorption, TLS everywhere, optional WAF.

Clarify: static only, or dynamic and video streaming too? Push or pull model?

Reference solution try it yourself first

APIs (control plane)

  • POST /distributions {origin, domains, cache_rules} → distribution id
  • POST /distributions/{id}/purge {paths} → 202 with purge id
  • Data plane: plain HTTP GET on the customer's domain

Data

  • Config store (strongly consistent, small): distributions, origins, cache rules, certificates. Replicated to every edge.
  • Edge cache: key = host + path + selected query params/headers; value = response + headers + expiry. RAM for hot objects, SSD for the rest.

Architecture (request path)

  1. DNS (GeoDNS or anycast) resolves to the nearest healthy point of presence (PoP).
  2. PoP load balancer hashes the URL (consistent hashing) to one cache server, so each object lives once per PoP.
  3. Hit → return. Miss → ask the regional shield cache.
  4. Shield miss → fetch from origin, collapse duplicate requests into one, cache at shield and edge.

Deep dives

  • Request collapsing: 1,000 simultaneous misses for the same object become one origin fetch.
  • Invalidation: control plane fans purge messages to all PoPs through a pub/sub bus; versioned URLs (app.v42.js) avoid purges entirely.
  • Eviction: LRU, with large rarely-hit objects evicted first.
  • Failure: health checks remove a PoP from DNS/anycast; if origin is down, serve stale content (stale-if-error).
  • Security: TLS terminated at the edge; DDoS absorbed across many PoPs; WAF rules at the edge.

Trade-offs to say out loud

  • Longer TTLs mean higher hit ratio but staler content.
  • Shield tier adds a hop but cuts origin load sharply.
  • Anycast fails over fast; GeoDNS gives finer control but is slowed by DNS caching.

Content sharing via unique URL

Clients upload directly to blob storage with a pre-signed URL; a metadata service assigns a short key; reads go through a CDN with access checks for private content.

Requirements

Functional

  • Users upload content: text, images, video, files.
  • Each upload gets a unique, short, shareable URL.
  • Anyone with the link (or only permitted users) can view the content.
  • Optional expiry and access control: public, private, password-protected.
  • Owners can delete or update their content.
  • Basic analytics: view counts.

Non-functional

  • Read-heavy: ~100:1 views to uploads.
  • Scale: ~10M uploads/day, ~1B views/day.
  • Low-latency reads worldwide (CDN for media).
  • Durability: uploaded content is never lost (replicated blob storage).
  • High availability for reads: 99.99%.
  • URLs are unique and hard to guess for private content.
  • Upload size limit, e.g. 100 MB per file.

Clarify: maximum file size? Do links need to be private by default?

Reference solution try it yourself first

APIs

  • POST /v1/content {type, size, visibility, expires_at?} → {content_id, upload_url (pre-signed), short_url}
  • PUT <upload_url> → client uploads bytes straight to blob storage
  • GET /{key} → 302 to a CDN URL (public) or a short-lived signed URL (private, after auth); 404 / 410 expired
  • DELETE /v1/content/{key} → 204 (owner only)

Data

  • Metadata (key-value store, e.g. Cosmos DB / DynamoDB, sharded by key): key, owner_id, blob_path, type, size, visibility, password_hash?, created_at, expires_at
  • Blobs in object storage (Azure Blob / S3), replicated across zones
  • View counts streamed to an analytics store, not written to the metadata row

Architecture

  1. Upload: client → API → metadata row (status=pending) + pre-signed URL → client uploads to blob → blob event marks status=ready (and triggers thumbnails or scanning).
  2. Read: client → CDN → API resolves key (cache-aside in Redis) → redirect to the blob via CDN.

Deep dives

  • Key generation: 7-char base62 from counter ranges (no collisions); use random 10+ char keys for private links so they can't be guessed.
  • Large files: chunked, resumable uploads; never stream bytes through app servers.
  • Private content: API checks permission, then issues a signed URL valid for minutes.
  • Expiry: checked on read; background job deletes expired blobs.
  • Abuse: rate limits per user, malware scan on upload.

Trade-offs to say out loud

  • Pre-signed uploads offload bandwidth but make validation asynchronous.
  • Sequential keys are short but guessable; random keys are safer but longer.

VM monitoring system

Agents push batched metrics to a regional ingestion tier backed by a partitioned log (Kafka / Event Hubs); stream processors write to a time-series database and evaluate alert rules; queries hit the time-series store.

Requirements

Functional

  • Agents on each VM collect metrics: CPU, memory, disk, network, plus custom metrics.
  • Ingest and store metrics as time series.
  • Query and graph metrics over time ranges, with aggregation (avg, p95, max).
  • Define alert rules (e.g. CPU > 90% for 5 min) and notify via email, pager or webhook.
  • Dashboards per VM, per group, per region.
  • Optionally feed autoscaling decisions.

Non-functional

  • Scale: ~1M VMs × ~100 metrics every 10 s ≈ 10M data points/sec ingested.
  • Write-heavy; reads are mostly recent data.
  • Alert latency: fire within ~1 minute of the condition.
  • Retention: full resolution for ~2 weeks, downsampled for ~1 year.
  • Ingestion must not lose data during spikes (buffer with a queue).
  • Monitoring must stay up when the monitored systems are failing.
  • Multi-tenant isolation: customers see only their own VMs.

Clarify: push (agents send) or pull (collector scrapes)? Logs too, or metrics only?

Reference solution try it yourself first

APIs

  • POST /v1/metrics (agent) — batch of {vm_id, metric, timestamp, value, tags}
  • GET /v1/query?vm=...&metric=cpu&from=...&to=...&agg=p95&step=1m
  • POST /v1/alerts {expression, duration, severity, channels}

Data

  • Time-series DB (e.g. Azure Data Explorer, InfluxDB, Prometheus-style TSDB): series key = metric + tags; points compressed (delta-of-delta timestamps, XOR values).
  • Rollups: raw for 14 days, 1-min for 90 days, 1-hour for 1 year.
  • Alert rules and dashboards in a small SQL store.

Architecture

  1. Agent on VM batches every 10 s, compresses, retries with backoff; buffers locally if the backend is down.
  2. Regional ingestion gateways authenticate and write to the log, partitioned by vm_id.
  3. Consumers write to the TSDB (sharded by series key + time).
  4. Stream processor evaluates alert rules on the live stream, keeps state per rule, deduplicates, then notifies.
  5. Downsampling jobs build rollups; query service picks the right resolution for the time range.

Deep dives

  • Write volume (10M points/s): batching, compression and the log absorb spikes; the TSDB is append-only.
  • Heartbeats: missing data for N intervals fires a "VM down" alert; silence is itself a signal.
  • Cardinality: limit tag values per tenant; high-cardinality tags (request IDs) explode storage.
  • Multi-region: data stays in its region; a global query layer fans out.
  • Self-monitoring: run the monitoring stack separately from what it monitors.

Trade-offs to say out loud

  • Push vs pull: push works through firewalls and scales with agents; pull gives the server control over load.
  • Stream alerting is fast; query-based alerting is simpler but adds delay.

E-commerce system

Split into services by consistency need: catalog and search (eventually consistent, heavily cached), cart (fast key-value), and order/inventory/payment (strongly consistent, transactional), coordinated by a saga over a message bus.

Requirements

Functional

  • Browse and search the product catalog.
  • Add to cart, update cart, check out.
  • Place orders and pay through a payment provider.
  • Track inventory; prevent selling more than is in stock.
  • Order history and status tracking (placed, shipped, delivered).
  • User accounts and addresses.

Non-functional

  • Scale: ~10M daily users, ~100K orders/day, 10× spikes on sales days.
  • Browsing and search: low latency (< 200 ms), eventual consistency is fine.
  • Orders, payments, inventory: strongly consistent, no double charges or oversells.
  • Idempotent checkout and payment calls.
  • Availability: 99.99% for browsing; checkout degrades gracefully, never loses an order.
  • Security: PCI compliance for payments, encrypted personal data.

Clarify (this question tests ambiguity): single seller or a marketplace? Which part to go deep on, catalog, cart or checkout?

Reference solution try it yourself first

APIs

  • GET /v1/products?q=...&cursor=... · GET /v1/products/{id}
  • PUT /v1/cart/items {product_id, qty}
  • POST /v1/orders {cart_id, address_id, payment_method} + Idempotency-Key header → 201 {order_id, status}
  • GET /v1/orders/{id}

Data

  • Catalog: document store + search index (Elasticsearch / Azure AI Search), CDN for images.
  • Cart: Redis or key-value store keyed by user_id, with TTL.
  • Orders, inventory, payments: SQL (Postgres / Azure SQL), sharded by user_id or order_id.
  • inventory(sku, available, reserved); orders(order_id, user_id, status, total, created_at).

Architecture (checkout saga)

  1. Order service creates order (status=pending) using the idempotency key.
  2. Inventory service reserves stock: UPDATE ... SET available = available - qty WHERE available >= qty (atomic, no oversell).
  3. Payment service authorizes through the provider.
  4. Success → order confirmed, event published for fulfillment and email. Failure → compensate: release stock, cancel order.

Deep dives

  • Oversell / flash sales: atomic conditional decrements; for hot SKUs, pre-split stock into buckets or queue purchases.
  • Double charge: idempotency keys end to end, including the payment provider call.
  • Reservation timeout: reserved stock released if payment doesn't finish in ~10 min.
  • Traffic spikes: autoscale stateless services, cache catalog aggressively, queue orders so checkout degrades instead of failing.
  • Search: index updated asynchronously from catalog change events.

Trade-offs to say out loud

  • Saga vs distributed transaction: saga avoids locking across services but needs compensation logic.
  • Stale price or stock on product pages is acceptable; checkout re-validates.

On-prem to cloud migration

Strangler-fig migration. Put a routing layer in front, move stateless services first, replicate data continuously into the cloud, shift traffic in small percentages with rollback at every step, then move the database primary last.

Requirements

Functional

  • Move services, databases and storage from on-prem to the cloud.
  • Keep every existing feature and API working for clients.
  • Migrate data with no loss, including data written during the migration.
  • Run on-prem and cloud side by side during the transition (hybrid).
  • Shift traffic gradually and roll back at any stage.
  • Decommission on-prem once the cloud path is verified.

Non-functional

  • Zero or near-zero downtime for customers.
  • Data consistency between old and new systems until cutover.
  • Same or better latency, availability and security after the move.
  • Cost: lower or predictable cloud spend versus on-prem.
  • Observability to compare old vs new behavior side by side.
  • Compliance: data residency rules per region.

Clarify: lift-and-shift or re-architect? Which parts are stateful? Hard deadline?

Reference solution try it yourself first

Plan in phases

  1. Assess: inventory services, dependencies, data size, which parts are stateful; classify each as rehost, replatform or re-architect.
  2. Foundation: cloud landing zone with networking (VPN / ExpressRoute to on-prem), identity, monitoring, infrastructure as code.
  3. Routing layer: global load balancer or API gateway in front of both environments, so traffic can be split by percentage or by tenant.
  4. Stateless services: containerize, deploy to the cloud, shift traffic 1% → 10% → 50% → 100% while comparing error rates and latency.
  5. Data: initial bulk copy, then change data capture (CDC) to keep the cloud copy in sync; validate with row counts and checksums.
  6. Database cutover: brief write freeze or dual-write window, promote the cloud database to primary, reverse replication back to on-prem as a rollback path.
  7. Decommission on-prem after a soak period.

Deep dives

  • Zero downtime: traffic shifting + CDC + reverse replication means every step can be undone.
  • Latency during hybrid: keep chatty services and their data on the same side; migrate them together.
  • Consistency: a single writer at any moment; avoid long dual-write periods (they drift).
  • Validation: shadow traffic (mirror real requests to the cloud and compare responses) before taking live traffic.
  • Rollback triggers: defined in advance by SLO (error rate, p99 latency).

Trade-offs to say out loud

  • Lift-and-shift is fast but keeps old inefficiencies; re-architecting saves cost long term but adds risk and time.
  • Migrating by tenant limits blast radius but runs both systems longer.

Message queue

Topics split into partitions; each partition is an append-only log replicated across brokers with a leader; consumers in a group own partitions and commit offsets; at-least-once delivery with idempotent consumers.

Requirements

Functional

  • Producers publish messages to named topics or queues.
  • Consumers receive messages, process them, and acknowledge.
  • Unacknowledged messages are redelivered after a timeout.
  • Consumer groups: each message goes to one consumer in a group; multiple groups each get a copy.
  • Dead-letter queue for messages that keep failing.
  • Optional: ordering within a partition, delayed messages, retention and replay.

Non-functional

  • Throughput: ~1M messages/sec across the cluster.
  • Latency: publish-to-deliver under ~10–50 ms.
  • Durability: acknowledged messages survive broker failure (replicated to disk).
  • Delivery guarantee: at-least-once by default; state it and make consumers idempotent.
  • Horizontal scaling through partitions.
  • Availability: 99.99%; broker failover without losing messages.

Clarify: queue (one consumer per message) or pub/sub? Is ordering required? Microsoft has also asked for interfaces and response classes, so be ready to sketch the API in code.

Reference solution try it yourself first

Interfaces (Microsoft has asked for these)

interface IProducer {
  Task<PublishResult> PublishAsync(string topic, Message msg, string? partitionKey = null);
}
interface IConsumer {
  Task<IReadOnlyList<Message>> ReceiveAsync(string topic, string group, int max, TimeSpan wait);
  Task AckAsync(string topic, string group, int partition, long offset);
}
record Message(string Id, byte[] Body, IDictionary<string,string> Headers, DateTime EnqueuedAt);
record PublishResult(string MessageId, int Partition, long Offset);

Data

  • Each partition: segment files on disk + an offset index. Messages kept for a retention period (e.g. 7 days), not deleted on read.
  • Metadata (topics, partition leaders, consumer group offsets) in a consensus store (ZooKeeper / Raft).

Architecture

  1. Producer hashes partition key → partition → sends to that partition's leader broker.
  2. Leader appends to its log, replicates to followers, acks once a quorum (e.g. 2 of 3) has it.
  3. Consumer group coordinator assigns partitions to consumers; each consumer reads sequentially and commits its offset after processing.
  4. Message fails N times → moved to a dead-letter topic.

Deep dives

  • Ordering: guaranteed only within a partition; same key → same partition.
  • Delivery: at-least-once (commit after processing); exactly-once needs idempotent producers plus transactional offset commits, or idempotent consumers.
  • Broker failure: controller promotes an in-sync follower to leader.
  • Throughput: sequential disk writes, batching, zero-copy reads; scale by adding partitions.
  • Rebalancing: adding a consumer triggers partition reassignment; brief pause in consumption.

Trade-offs to say out loud

  • Acking after quorum is safer but slower than acking on leader write.
  • More partitions give more parallelism but weaker overall ordering and more metadata.

Real-time collaborative document editing

Clients hold WebSocket connections to a collaboration server that owns each open document; edits are operations merged with OT (or CRDTs), appended to an operation log, broadcast to other editors, and periodically snapshotted.

Requirements

Functional

  • Create, open and edit documents or spreadsheets.
  • Multiple users edit the same document at once and see each other's changes live.
  • Show presence: who is viewing, cursor positions.
  • Resolve conflicting edits so everyone converges to the same document.
  • Version history and restore.
  • Sharing and permissions: owner, editor, viewer.

Non-functional

  • Edits appear to other users within ~100–200 ms.
  • Up to ~100 concurrent editors per document; millions of documents.
  • No lost edits, even with dropped connections (offline edits sync later).
  • Strong eventual consistency: all clients converge.
  • Durability: every saved change persisted and replicated.
  • Availability: 99.99%.

Clarify: text documents or spreadsheets (formulas add dependency recalculation)? Offline editing needed? Key deep dive: operational transformation (OT) vs CRDTs.

Reference solution try it yourself first

APIs

  • POST /v1/docs · GET /v1/docs/{id} (latest snapshot + version) · POST /v1/docs/{id}/share
  • WebSocket /v1/docs/{id}/live: client sends {op, base_version}; server sends {op, version, author}, presence and cursor updates

Data

  • Operation log (append-only, per document): doc_id, version, op, user_id, timestamp
  • Snapshots every N ops or minutes, in blob storage; version history = snapshots + ops
  • Doc metadata and permissions in SQL

Architecture

  1. Client opens the doc: load the latest snapshot plus ops since, then connect the WebSocket.
  2. Gateway routes all editors of one doc to the same collaboration server (consistent hashing on doc_id).
  3. Client applies its edit locally at once, sends the op with its base version.
  4. Server transforms the op against ops it hasn't seen, assigns the next version, persists, broadcasts.
  5. Presence (cursors) sent via the same channel but never persisted.

Deep dives

  • OT vs CRDT: OT needs a central server to order ops (simpler for server-based apps; Google Docs uses it). CRDTs merge without a central order (better for offline and peer-to-peer) but carry more metadata.
  • Server failure: a new server takes over the doc by replaying the op log from the last snapshot; clients reconnect and resend unacknowledged ops.
  • Offline: client queues ops, transforms them against missed ops on reconnect.
  • Spreadsheets: cell-level ops are simpler than text, but formula dependencies need a recalculation graph.
  • Scale: millions of docs, few editors each, so shard by doc_id.

Trade-offs to say out loud

  • One server per doc makes ordering easy but creates a hot spot for very popular docs.
  • Frequent snapshots load faster but cost more storage.

Cloud file storage (OneDrive-style)

Split files into content-addressed chunks stored in blob storage; a metadata service tracks files, versions and which chunks make each version; a sync service notifies devices of changes so they download only the chunks that changed.

Requirements

Functional

  • Upload, download, delete files and folders.
  • Sync files across a user's devices automatically.
  • Share files or folders with other users, with permissions.
  • File version history.
  • Resumable uploads for large files.
  • Notify devices when a file changes.

Non-functional

  • Scale: ~100M users, ~10 GB average each ≈ 1 EB stored.
  • Durability: 11 nines; files are never lost (replication, erasure coding).
  • Large files up to ~50 GB, uploaded in chunks.
  • Sync latency: changes appear on other devices within seconds.
  • Bandwidth efficiency: sync only changed chunks, deduplicate identical chunks.
  • Consistency: last writer wins or conflict copies; never silently lose an edit.
  • Availability: 99.9%+; security with encryption at rest and in transit.

Clarify: sync client in scope or web only? Is sharing in scope? Metadata service and chunked block storage are the usual deep dives.

Reference solution try it yourself first

APIs

  • POST /v1/files/upload-session {path, size, chunk_hashes[]} → which chunks are missing + upload URLs
  • PUT <chunk_url> → upload each missing chunk (resumable)
  • POST /v1/files/commit {session_id, base_version} → new version, or 409 on conflict
  • GET /v1/changes?cursor=... → changes since the device's last cursor (plus long-poll or push notification)
  • GET /v1/files/{id}?version=... → chunk list + download URLs

Data

  • Metadata (SQL, sharded by user_id): files(file_id, owner_id, path, latest_version), versions(file_id, version, chunk_list, size, created_at), shares(...), plus a per-user change journal for sync cursors
  • Chunks (~4 MB) in blob storage keyed by SHA-256 hash, so identical chunks are stored once

Architecture

  1. Client splits the file into chunks, hashes them, asks which are new.
  2. Uploads only missing chunks directly to blob storage.
  3. Commits the new version in metadata (conditional on base_version).
  4. Change journal records it; notification service pushes to the user's other devices.
  5. Other devices fetch changes by cursor, download only new chunks, reassemble.

Deep dives

  • Dedup and delta sync: content hashes mean edits to a large file upload only changed chunks.
  • Conflicts: commit fails on a stale base_version; the client saves a "conflicted copy" instead of overwriting.
  • Durability: blob storage with zone or geo replication and erasure coding; never delete a chunk while any version references it (reference counting + garbage collection).
  • Hot metadata: cache folder listings; shard by user so one user's tree stays together.
  • Sharing: shared folders appear in each user's change journal via fan-out on write.

Trade-offs to say out loud

  • Smaller chunks give better dedup but more metadata and requests.
  • Cross-user dedup saves storage but complicates encryption and privacy.
